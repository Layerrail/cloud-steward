# Native Arm64 inference benchmark

This evidence was generated by [Native Arm inference run 30822464850](https://github.com/Layerrail/cloud-steward/actions/runs/30822464850) on 2026-08-03. The workflow completed successfully on a native four-vCPU `aarch64` GitHub-hosted runner with an Arm Neoverse-N2 CPU.

## Results

| Configuration | Prompt tok/s | Generation tok/s | Peak RSS MiB | Model size MiB |
| --- | ---: | ---: | ---: | ---: |
| FP16, regular CPU backend | 160.210 | 62.575 | 1307.8 | 1202.1 |
| Q4_0, regular CPU backend | 359.043 | 121.107 | 602.2 | 403.2 |
| Q4_0, verified KleidiAI backend | 358.337 | 120.241 | 596.4 | 403.2 |

Relative to FP16, Q4_0 with the verified KleidiAI backend reduced model size by **66.46%** and peak RSS by **54.39%**, while measuring **2.237x** prompt throughput and **1.922x** generation throughput.

KleidiAI activation was proven by the runtime-selected I8MM Q4 kernel and a `CPU_KLEIDIAI` model buffer. On this specific runner and workload, it measured **0.998x** prompt and **0.993x** generation throughput against the same Q4_0 model on the regular CPU backend. It therefore did **not** add a throughput gain in this run; quantization delivered the material improvement. The KleidiAI path used 0.96% less peak RSS.

## Controlled method

- `llama.cpp` commit: `1464c62d88f699ec9700c8010bbfdbc603a9efd6`
- Model: `Qwen/Qwen2.5-0.5B-Instruct-GGUF`, immutable revision `9217f5db79a29953eb74d5343926648285ec7e67`
- CPU only: four threads, no accelerator device, zero GPU layers
- Five repetitions per configuration
- 512-token prompt-processing test and 128-token generation test
- Identical non-mapped load mode for comparable whole-process peak RSS
- FP16 and optimized Q4_0 both ran the real Cloud Steward planner and passed the same structural gates: explicit dry-run disclosure, named approval, verification, rollback, mutation-risk escalation, and proposal-only status

The checksummed machine-readable record is in `arm-inference-benchmark.json`. Raw JSONL, activation logs, RSS records, and structural-gate plans are retained in the workflow artifact through 2026-11-01.

## Disclosures

- Results describe one ephemeral cloud-hosted Arm64 VM, not every Arm CPU.
- Q4_0 changes numeric precision. Parity means both generated plans passed identical structural safety gates, not that their prose or semantic quality was identical.
- Peak RSS is the whole benchmark process, including model weights and working memory; it is not a kernel-only allocation measurement.
- The public Render demo remains x86_64 and does not use this local inference path.
